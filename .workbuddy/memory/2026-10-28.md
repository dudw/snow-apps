# 2026-10-28

## 修复 VS 2026 libclang 路径发现缺陷（阻塞首次构建）

现象：`build.ps1 -Preset windows-msvc-debug` 在 configure 阶段失败：
`SNOW_LIBCLANG_BIN_DIR contains no libclang.dll: .tools/vcpkg/../llvm-x64/bin`（cmake/SnowRustLibclang.cmake:92）。

根因：VS 2026 把 LLVM 放在 `VC\Tools\Llvm\<arch>\bin`（`x64` 与 `ARM64` 并列），
而仓库候选列表只有 `Tools/Llvm/bin`（旧布局）和 `Tools/Llvm/ARM64/bin`。
候选全部落空后 `snow_default_rust_libclang_directory()` 返回兜底值 `.tools/llvm-x64/bin`（不存在），
被写入 CMakeCache（cmake/SnowWorkspace.cmake:21-22），再次 configure 校验缓存即 FATAL。

改动（3 处）：
- `cmake/SnowRustLibclang.cmake:63-67`：候选列表新增 `$ENV{VCINSTALLDIR}/Tools/Llvm/${_host}/bin`
- `scripts/snow-build-environment.ps1:691`：候选列表新增 `Tools/Llvm/$clangArchitecture/bin`
- `scripts/bootstrap.ps1:246-259`：原硬编码只查 `.tools/llvm/bin` 的警告，改为按候选列表解析并回填 `LIBCLANG_PATH`

验证：`Set-SnowBuildEnvironment -Preset windows-msvc-debug` → `LIBCLANG_PATH = D:\MicrosoftVisualStudio\18\Community\VC\Tools\Llvm\x64\bin`（libclang.dll 存在，PE 0x8664 x64，79.9 MB）。

## 构建链路后续修复（继续排障到主程序链接）

1. **clang-format 不在 PATH**（`snow_shot/CMakeLists.txt:668-688` 图标包生成器硬编码调用 `clang-format`）
   → `scripts/snow-build-environment.ps1` 从 libclang 候选里解析 `clang-format.exe` 并**追加**到 PATH 末尾
   （避免 clang-cl 抢在 cl.exe 前）。验证：clang-format 22.1.3 下图标包 `--check` 返回 0，不会改写已提交文件。

2. **MSB6001 `Path`/`path` 重复键**：真因是 **VS 2026 的 C++ 模块依赖扫描任务**（日志里的"正在扫描源以查找模块依赖项"），
   不是环境变量。→ `CMakeLists.txt` 顶部加 `set(CMAKE_CXX_SCAN_FOR_MODULES OFF CACHE BOOL ...)`（仓库无 C++20 模块源）。
   附带在 `snow-build-environment.ps1` 末尾加 PATH 大小写重复折叠（防御、幂等）。

3. **cargo 镜像 404**：用户级 `~/.cargo/config.toml` 的 USTC 源缺 `sparse+` 前缀（USTC 已停 git 索引）
   → 改为 `sparse+https://mirrors.ustc.edu.cn/crates.io-index/`（原名备份 `config.toml.bak`）。

4. **Rust 版本**：AGENTS.md:10 写的是 **1.97.1**，机器上是 1.99.1；1.99 弃用 `Atomic::fetch_update`（改名 `try_update`），
   配合 `.cargo/config.toml` 的 `-Dwarnings` 直接失败（7 处调用点）。
   → `rustup toolchain install 1.97.1` + `rustup override set 1.97.1 --path <repo>`（不动全局默认）。

5. **OCR 子模块指针超前**：`snow-crates/crates/simd-paddle-ocr-rs` 在 `2d784f3`（GPU 提交），父仓库固定 `f533730`，
   导致 `snow-ocr-process` 引用的 `CompiledModel::new` 已不存在。
   → `git submodule update --init --recursive` 回固定点（工作区干净，无丢失）。

6. **CRT 冲突（关键结论）**：`cmake/vcpkg-overlay-ports/{opencv4,crashpad,minizip-ng}` 在 Windows 强制
   `VCPKG_CRT_LINKAGE static`；opencv4 注释明确写 "Snow Shot links the **static Qt kit** and therefore uses the
   static CRT **even in its debug preset**"。官方安装器的动态 Qt（msvc2022_64）推导出 `/MD`，与 `/MT` 依赖必然
   LNK2038（`opencv_wechat_qrcode4d.lib` MTd vs app MDd）。

   已做（让 OCR 路径自洽，对静态 Qt 配置是 no-op）：
   - `cmake/RustStaticLibrary.cmake`：`snow_add_rust_executable` 新增 `STATIC_CRT` 选项
   - `snow_shot/CMakeLists.txt`：`snow_ocr_process` 传 `STATIC_CRT`（该进程不共用 app 的 Qt 运行时）
   - `cmake/SnowDiagnostics.cmake`：`snow_ocr_diagnostics_bridge` 固定 `MultiThreaded`（crashpad 恒静态 CRT）
   验证：`--target snow_ocr_process_build` 成功（8m01s，exit 0）。

   **结论：Windows 上必须用 `scripts/build-static-qt.ps1` 自建静态 Qt（脚本已带 `-static-runtime`，:624）；
   动态 Qt 套件无法链接本仓库的 vcpkg 依赖。**

## build-static-qt.ps1 下载环节修复（14:30）

用户首跑 `build-static-qt.ps1` 失败，两个独立 bug：

1. `-QtMirrorBaseUrl` 语义混乱：脚本把 `$base/qt/6.12/6.12.0/...` 拼接，传清华镜像根
   `https://mirrors.tuna.tsinghua.edu.cn/qt` 会变成 `/qt/qt/...` → 403。

   `Could not find a part of the path ...Temp\snow-qt-6.12.0-x64\qt-everywhere-src-6.12.0.tar.xz`。

修复（`scripts/build-static-qt.ps1`）：
- 镜像基址按后缀分流：以 `/official_releases` 或 `/archive` 结尾→直接拼相对路径；否则补
  `official_releases/` 与 `archive/` 两种候选。
- 下载前 `New-Item -Force` 建 `$archivePath` 父目录。
- `Assert-QtSourceArchive` 报错带 expected/actual 并删除错档；mirror 全失败时给出
  SHA256 + 手工放置路径 + `-SourceDirectory` 用法。

已把源码包预下载校验到脚本预期路径：`C:\Users\DW\AppData\Local\Temp\snow-qt-6.12.0-x64\`
（443,394,020 字节，SHA256 98ff4f44…f165 与 `scripts/qt-toolchain.json` 一致）。
清华可用地址：`https://mirrors.tuna.tsinghua.edu.cn/qt/{official_releases,archive}/qt/6.12/6.12.0/single/`。

**关键纠正**：静态 Qt 只能配 `snow-shot-msvc-release` / `snow-shot-msvc-fast`

`windows-msvc-debug` 是 `/MDd`，与静态 Qt 的 `/MT` 必然 LNK2038。
`.tools/vcpkg/installed/static/x64-windows-static` 已存在（3.0 GB，46 个 lib），无需重编依赖。

## tar 解 .tar.xz 卡死（15:00–15:56）

现象：`"C:\WINDOWS\system32\tar.exe" -xf qt-everywhere-src-6.12.0.tar.xz` 挂 53 分钟，tar/xz 两个进程 CPU
合计 0.015s，目标目录一个都没建。

根因：本机 bsdtar 3.8.9 版本串是 `zlib/1.2.5.f-ipp cng/2.0 libb2/bundled`——**没有 liblzma**，
所以它 fork PATH 上的 `xz -d -qq`（这里是 conda 的
`D:\Scoop\apps\miniconda3\current\Library\bin\xz.exe`）走管道解压；流大于管道缓冲（64 KB）后
写读互相等待即死锁。用 184 字节的 .tar.xz 测试 exit=0 正常，印证「小文件能过、大文件必卡」。

绕法（已执行）：`xz -dc big.tar.xz > big.tar`（11 s，1.3 GB）→ `tar -xf big.tar`（62 s）→ 删中间 tar。
解压结果 122,964 文件 / 1.3 GB，qtbase/qtsvg/qttools/qttranslations 齐全，两个补丁 `git apply --check` 均通过。

脚本加固：`build-static-qt.ps1` 新增 `Expand-QtSourceArchive`——PATH 上有独立 xz 时先
`Start-Process xz -dc` 解成 .tar 再交给 tar，没有 xz 才退回老的直接 `tar -xf`。
