## 静态 Qt 偷偷链接 conda 的 pcre2/zstd（11:20–11:45）

### 实证

`dumpbin /dependents` 打在 09:28 生成的 `snow_shot.exe`（88,567,808 B）上，导入表里有
**`pcre2-16.dll` 与 `zstd.dll`**，而 `Release` 目录 **0 个 .dll**。两个 DLL 只存在于
`D:\Scoop\apps\miniconda3\current\Library\bin`（在 PATH 上）→ 这个"静态"exe 换台机器就起不来。
上游证据：`CMakeCache.txt` 的 `PCRE2_DIR` / `zstd_DIR` 都指向 conda；链接命令行里的
`pcre2-16.lib`(22 KB)、`zstd.lib`(45 KB) 都是 import lib。根因是构建 Qt 时 conda 在 PATH，
`static-qt-features.json` 只钉死了 `system_png`/`system_zlib`（vcpkg），pcre2/zstd 交给自动探测。

### 纠正一个想当然的方案

`-DQT_FEATURE_zstd=qt` **不存在**：`qtbase/src/3rdparty/` 有 `pcre2` 但**没有 zstd**，
`qtbase/configure.cmake` 是 `qt_find_package(WrapZSTD 1.3 MODULE ...)`，`FindWrapZSTD.cmake`
只做 `find_package(zstd CONFIG QUIET)`，vcpkg 静态三元组也没装 zstd。zstd 只能"接外部静态库"
或"关掉"，没有 bundled 选项。

### 采用的改法

- `build-static-qt.ps1`：加 `-qt-pcre` 与 `-no-feature-zstd`；另加
  `-DCMAKE_DISABLE_FIND_PACKAGE_PCRE2/WrapSystemPCRE2/zstd=ON` 双保险；configure 后 4 条断言
  （`FEATURE_pcre2:BOOL=ON`、`QT_FEATURE_pcre2:INTERNAL=ON`、
  `QT_FEATURE_system_pcre2:INTERNAL=OFF`、`QT_FEATURE_zstd:*=OFF`）。
- `static-qt-features.json`：`pcre2:true`、`system_pcre2:false`、`zstd:false`。
- `snow-build-environment.ps1`：`zstd` 是 PUBLIC feature，已加进 `$visibility` 的 PUBLIC 集合。
- `test-static-qt-features.ps1`：mock 补 `QT_ENABLED_PRIVATE_FEATURES "pcre2;..."`、
  `QT_DISABLED_PUBLIC_FEATURES "zstd"`、`QT_DISABLED_PRIVATE_FEATURES "system_pcre2;timezone_locale"`，
  4 处 `-replace` 锚点同步；`Static Qt feature policy tests passed.`

关掉 zstd 的代价：Qt 里它只服务 rcc 的 zstd 压缩、mimetype 数据库、QtNetwork 的
`Content-Encoding: zstd`；`snow_shot` 源码零引用。

### 静态 Qt configure 失败：结论是「改用 Ninja」，不是修 nmake

现象：`Qt configuration does not satisfy Release LTCG policy`，往上看是
`Check for working CXX compiler ... - broken`，nmake 报
`U1052: 找不到文件 CMakeFiles\cmTC_xxxx.dir\build.make`。

排查过程中的几条硬事实（都实测过）：

1. 环境块里 `Path` 与 `path` 并存，`cmake -E env` 取的是**旧的**那条：父进程 `$env:Path`
   1648 字符含 MSVC，`cmake -E env <python>` 里只有 1618 字符、不含 MSVC。所以
   `cmake -E env VERBOSE=1 nmake` 连 nmake 都找不到（复现出 `no such file or directory`）。
2. 但**给 nmake 换成绝对路径并不能解决**——用户重跑后 nmake 已是绝对路径，仍然
   `U1052: CMakeFiles\cmTC_*.dir\build.make`。说明 NMake 生成器那条链路本身在这台机器上不可靠
   （Qt 自己也在 configure 里警告：官方只支持 Ninja，用 NMake 风险自负）。
3. 探针踩过的坑：脚本调的是**根目录** `configure.bat`，而 `qtbase/configure.bat -top-level`
   会把 `TOPQTDIR` 算成 **cwd 的父目录**（`for %%P in ("%CD%") do set TOPQTDIR=%%~dpP` 后
   `cd "%TOPQTDIR%"`）。直接调 qtbase/configure.bat 会让构建目录跑偏到 `%TEMP%`，
   我据此得到的"EXIT=0 成功"是假阳性，还把 `%TEMP%` 污染出一份 CMakeCache。

修法（`scripts/build-static-qt.ps1`，已验证）：

- 新增 `Resolve-CMakeGenerator -Preference`，返回 `{Name, Program}`：优先 Ninja
  （PATH 上有就用；否则取 `$env:VSINSTALLDIR\Common7\IDE\CommonExtensions\Microsoft\CMake\Ninja\ninja.exe`），
  可选 NMake 兜底；新参数 `-CmakeGenerator Auto|Ninja|'NMake Makefiles'`，默认 Auto。
- configure 显式传 `-cmake-generator <name>`（不传时 configure 会自动挑，实测在 PATH 看不到
  cl 的 shell 里挑成了 `MinGW Makefiles`），`--` 段再给 `-DCMAKE_MAKE_PROGRAM=<绝对路径>`。
- cache 断言：`CMAKE_GENERATOR:INTERNAL=<name>` + `CMAKE_MAKE_PROGRAM` 必须是绝对路径
  （Ninja 下该键类型是 `UNINITIALIZED`，正则已兼容）。

验证：用根 `configure.bat`（cwd=构建目录）+ `-cmake-generator Ninja` 完整跑通，
`EXIT=0`、`Generating done`、`CMakeCache.txt` 生成，且脚本里所有断言键实测取值都对得上：
`CMAKE_GENERATOR:INTERNAL=Ninja`、`FEATURE_ltcg:BOOL=ON`、`QT_FEATURE_ltcg:INTERNAL=ON`、
`FEATURE_pcre2:BOOL=ON`、`QT_FEATURE_system_pcre2:INTERNAL=OFF`、`QT_FEATURE_zstd:INTERNAL=OFF`、
`FEATURE_system_png/zlib:BOOL=ON`、`QT_FEATURE_concurrent/linguist/timezone:INTERNAL=ON`、
`FEATURE_timezone_locale:BOOL=OFF`。

排障中另有两个 PowerShell 陷阱值得记住：

- 变量名大小写不敏感：`$cmakeGenerator` 与参数 `$CmakeGenerator` 是同一个变量，赋值时会被
  参数的 `ValidateSet` 拒掉（报"该值不是变量 CmakeGenerator 的有效值"），改名 `$buildGenerator`。
- 管道只有一个元素时会被展开成标量，`$list[0]` 取到的是**字符串首字符**
  （`Program` 变成 `D`），必须 `@(...)` 包一层再用 `.Count`/`[0]`。

### 静态 Qt 已建成 + 新增 build.cmd 打包入口

`.tools/qt/6.12.0/msvc2026_64-static` 现已是完整套件（3.5 GB，`lib/cmake/Qt6/Qt6Config.cmake`

新增仓库根 `build.cmd`（CRLF、纯 ASCII 输出），动作：

- `package`（默认）→ `package-snow-shot.ps1 -Architecture -Parallelism [-SkipBuild] [-BuildDirectory]`
- `build` → `build.ps1 -Preset [-Clean] [-Reconfigure] [-Target]`
- `qt` / `all` → `build-static-qt.ps1 -Configuration Release -Architecture x64 -InstallPrefix .tools\qt\6.12.0\msvc2026_64-static [-CmakeGenerator] [-Force]`

批处理语法坑（都踩过并规避）：

- **文件必须 CRLF**；用 LF 保存的 .cmd 直接报"命令语法不正确"且整段不执行。

- 套件名区分架构：含 `arm64` → arm64 套件，否则 x64。

`Configuring done (115.8s) / Generating done (3.9s)`，写盘 `build/snow-shot-msvc-release`，
没有 rules.ninja 类问题（VS 生成器不走 include 链）。完整 LTCG 编译+链接留给用户终端；
`GenerateDebugInformation=DebugFull` 仍可能触发之前那次 link 空转，必要时改 `false`。

### 打包卡在 shaderc-sys 找不到 ninja（已修复并验证）

现象：`build.cmd`（package / snow-shot-msvc-release）在 `snow_ocr_process_build` 阶段 panic
`couldn't find required command: "ninja"`（shaderc-sys 0.10.1 build script，exit 101），MSBuild 报 MSB8066。

根因（实测确认，非推断）：

- OCR worker 启用 `gpu` feature ⇒ shaderc 走 build-from-source，其 build script 用 `cmd_finder`
  校验 PATH 上的 cmake/git/python/ninja，并强制 Ninja 生成器。
- VS 自带 `Common7\IDE\CommonExtensions\Microsoft\CMake\Ninja`，但**不在 PATH**。
- 更关键：VS 生成器的 `CustomBuild` 步骤**没有把调用方 PATH 传给 cargo 子进程**（在 vcxproj 的
  自定义命令里插 `where` 探测，输出为空）。只改 PowerShell 的 `$env:Path` 无效，必须在 cargo
  命令行里显式注入。
- 注入后进一步暴露 `rc` 资源编译器缺失（`RC Pass 1 failed: no such file or directory`），
  说明丢掉的是整段开发者 PATH，而不是只有 ninja 一项。

修复：

1. `cmake/SnowWindowsArchitecture.cmake` 新增 `snow_windows_ninja_directory()`（`SNOW_NINJA_DIR` /
   `VSINSTALLDIR` 提示 + `find_program`）；`snow_windows_rust_environment()` 把配置期 PATH 逐条以
   `--modify PATH=path_list_prepend:<dir>` 注入 cargo 环境。要点：整串 `PATH=...` 会被
   `COMMAND_EXPAND_LISTS` 按分号拆成多个参数；`--modify` 必须是两个相邻参数（`--modify=...`
   单参数写法 cmake 报 unknown option）；逆序遍历以保持原 PATH 顺序。
2. `scripts/snow-build-environment.ps1` 新增 `Get-SnowNinjaSearchDirectory` /
   `Resolve-SnowNinjaExecutable`，在 `Set-SnowBuildEnvironment` 中补 PATH 并导出 `SNOW_NINJA_DIR`；
   找不到只告警（有 Vulkan SDK 时 shaderc 不需要 ninja）。
3. 测试：`scripts/test-build-toolchain.ps1` 增加 ninja 解析确定性用例；
   `scripts/test-windows-architecture.py` 增加
   `test_rust_environment_carries_developer_path_for_build_scripts`，并把 `run_cmake` 改为
   `encoding='utf-8'`（CMake 输出 UTF-8，GBK 默认解码遇到中文路径会炸）。
4. 文档：`docs-windows-arm64-build.md`、`simd-paddle-ocr-rs/docs/gpu-usage.md` 补 Ninja/Git 前置。

验证：清理 shaderc-sys 缓存后 `build.ps1 -Preset snow-shot-msvc-release -Target
snow_ocr_process_build` 从源码编完 shaderc 并链接成功（exit 0）；`WindowsArchitecture` 23 项测试通过；
`test-build-toolchain.ps1` 通过。

遗留：`build/ninja-probe-target`（约 2GB，排查用临时 CARGO_TARGET_DIR）待删，批量删除需用户确认。

### 第二个阻塞：unity 构建下的匿名命名空间重名（已修复）

`snow_shot_settings_mini` 编译 `unity_3_cxx.cxx` 报 C2668：`validation` 调用不明确。
原因：`src/presentation/services/globalshortcutbackend.cpp` 与
`src/platform/windows/globalshortcutbackend.cpp` 各自在 `namespace snow_shot::presentation { namespace { ... } }`
里定义了 `validation`，前者三参带默认值，unity 合并成一个 TU 后两参调用二义。
macOS 的 `platform/macos/globalshortcutbackend.cpp` 有同样写法，属于同类隐患。

修复：把通用回退实现改名并简化为 `unsupportedValidation(binding)`（固定 supported=false、
reason=UnsupportedPlatform），调用点同步。`snow_shot_settings_mini` 目标现已编译+链接通过。

附带事实：
- MSB8027（`globalshortcutbackend.cpp`、`focusedfullscreenwindow.cpp` 同名文件同输出）是既有告警；
  vcxproj 里这些条目是 `IncludeInUnityFile=true`，实际只通过 unity_*.cxx 编译，不会重复产出 obj。
  根治需重命名平台回退文件，暂未动。
- MSB6001“字典中的关键字 Path 与 path 冲突”不是仓库问题：沙箱 PowerShell 进程自带
  `path`/`Path`/`PATH` 三个变体，MSBuild ToolTask 会炸；先合并成一个再跑即可。用户终端无此现象。
- 背景终端任务约 10 分钟被终止，完整 `snow_shot` 目标（LTCG）在本会话无法跑完，
  已确认失败点之前的 unity 单元全部通过（`snow_shot_settings.lib` 已产出）。

### 第三个阻塞：打包时 cargo metadata --offline 缺 crate（已解决，非代码问题）

打包收尾阶段 `collect-third-party-licenses.ps1` 报 `failed to download anes v0.1.6 /
--offline was specified`。原因链：
- `cargo metadata` 对 workspace 成员会解析**整个 workspace**，包含所有成员及其 dev-dependencies；
  `criterion 0.5` 是 `snow-capture` / `snow-audio-recorder` 的 dev-dep，`anes` 是 criterion 的传递依赖。
- 基准测试从不参与常规构建，因此这些 crate 从未下载进 `~/.cargo` 缓存；而许可证脚本刻意用
  `--locked --offline` 保证可复现，于是元数据解析直接失败。

解决：在 `snow-crates` 执行 `cargo fetch --locked --target x86_64-pc-windows-msvc` 预热缓存
（走 USTC 镜像，可下载）。之后离线 `metadata`/`tree` 均 exit 0；单独跑许可证收集脚本输出
“615 notices for 283 Rust packages and 21 vcpkg packages, plus Qt”，exit 0。

可选的仓库加固（未实施，需确认）：在 `bootstrap.ps1` 加 `cargo fetch --locked`（含 OCR 子模块
workspace），让“一次性环境准备”覆盖离线许可收集的前置；或让收集脚本在离线失败时回退联网一次。

其他坑：用 Windows PowerShell 5.1 跑 `collect-third-party-licenses.ps1` 会报
`[System.IO.Path]` 无 `GetRelativePath`（.NET Framework 缺该方法），必须用 pwsh 7；
`build.cmd` 已优先选 pwsh，没问题。
